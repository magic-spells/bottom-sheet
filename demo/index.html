@magic-spells/bottom-sheet

A sheet with momentum.

A bottom sheet built on the native dialog. It follows the pointer, dismisses on a flick, steps aside for scrolling content, and keeps its footer above the safe area.

Install npm install @magic-spells/bottom-sheet
Uses @magic-spells/dialog-panel
Anatomy 3 nested elements

Three layers, and only one of them moves.

<dialog-panel> owns the modal layer — focus trap, Escape, backdrop, body scroll lock. The native <dialog> is the surface that slides. <bottom-sheet> sits inside it and turns pointer gestures into a transform on that surface.

Inside the sheet, the header is the drag handle — it draws the rounded bar and takes touch-action: none so a downward drag never gets read as a scroll. The content below it flexes and scrolls on its own. 

<dialog-panel id="sheet-panel">
  <dialog aria-labelledby="sheet-title">
    <bottom-sheet>
      <bottom-sheet-header>
        <h2 id="sheet-title">A useful title</h2>
        <button data-action-hide-dialog aria-label="Close">&times;</button>
      </bottom-sheet-header>
      <bottom-sheet-content>…</bottom-sheet-content>
    </bottom-sheet>
  </dialog>
</dialog-panel>

// the trigger is passed in so focus returns to it on close
sheet.show(trigger)
Release 0.5 px/ms · 100px

Let go, and the sheet decides.

Two independent rules run on release, and either one dismisses. A flick only needs speed: downward velocity above 0.5 px/ms, measured over the last 100ms of the gesture, so a short sharp swipe closes without travelling far. A pull only needs distance: more than 100px down, with release velocity still above -0.05 px/ms — that second clause is what lets you change your mind. Drag past the threshold, reverse upward, and the sheet snaps home.

Cancelled gestures always snap back. Upward drags never dismiss; they get a square-root rubber band instead of tracking the pointer one-to-one.

Both rules are conditional once snap points exist. On a snapping sheet a flick doesn't dismiss — it steps one snap in its own direction, and only runs out of snaps at the shortest one. The 100px pull is measured below that shortest snap rather than from wherever the sheet happened to be sitting.

Waiting for a release… 
// bottom-sheet.js — either rule dismisses
const flick    = velocityY > 0.5;
const pastPull = deltaY > 100 && velocityY > -0.05;

if (flick || pastPull) sheet.hide();
else dialog.style.transform = ''; // snap back
Handoff mid-gesture

The list runs out, and the panel picks it up.

A sheet full of list items has two plausible readings of a downward drag: scroll the list, or move the panel. The sheet re-asks that question on every move until one of them wins, so the answer can change part way through a single continuous gesture. Scroll up through the list, hit the top, and keep pulling — the panel takes over from there without you lifting a finger.

The distance already travelled is recorded as claimOffset at the moment of the handoff and subtracted from everything after it. Without that the panel would jump by however far you'd already scrolled. Once the panel has claimed a gesture it keeps it until release — the handoff only ever runs one way.

deltaY is cumulative, so its sign only reports where the pointer sits relative to where it started. The claim test needs to know which way it's travelling right now, which is why DragGesture reports moveY alongside it. 

// re-asked on every move until it succeeds
if (moveY > 0) return content.scrollTop === 0;  // hand off at the top

// upward: below the tallest snap, growing beats scrolling
return snaps.length > 0 && activeSnap < snaps.at(-1);

// on the move that wins, remember where it started
drag.claimOffset = deltaY;
const travel = deltaY - drag.claimOffset;
Snap 40 · 70 · 90 dvh

Three resting heights, and the sheet picks one.

Give the sheet snap-points="40,70,90" and it stops being a two-state thing. Each number is a percentage of the viewport height, and it becomes the height of the dialog rather than a distance to push it down by. That choice is what keeps the footer pinned to the bottom edge at every snap and keeps the scrollable region exactly as tall as the part you can actually see.

On release, a flick steps exactly one snap in its own direction — never two, however hard you throw it — and anything slower lands on whichever snap is nearest. Stepping is measured from where the sheet is, not from the snap the gesture started at, so dragging from 40 up past 90 and flicking up doesn't fall backwards to 70.

Dragging below the shortest snap stops being a resize and becomes the ordinary dismiss gesture, on the same transform path a sheet with no snap points uses. That's the only place the sheet can close from.

The resting height is written as a dvh string rather than pixels, so rotating the device or opening the URL bar re-resolves it for free — there's no resize listener behind this at all.

Not open yet… 
<bottom-sheet snap-points="40,70,90">…</bottom-sheet>

// the current snap reflects back, on commit only
sheet.snap          // 70
sheet.snapPoints    // [40, 70, 90]
sheet.snapTo(90);

sheet.addEventListener('snapChange', (e) => {
  console.log(e.detail); // { from: 70, to: 90 }
});
Composite 25 · 55 · 92 dvh

All of it, doing one job.

The mechanics above are easier to trust when they're not in isolation. This is the shape every maps app converges on: a sheet that opens at a peek, a search field in the fixed header, and a results list that scrolls once there's room for it to.

At the 25dvh peek there's barely a list to scroll, so dragging up on the content grows the sheet instead of scrolling it — you expand first, then scroll, which is the behaviour your thumb already expects. Only at the tallest snap does an upward drag go back to being an ordinary scroll. A sheet with no snap points declared never takes that branch, so nothing about this changes the plain case. 

<bottom-sheet snap-points="25,55,92" snap="25">
  <bottom-sheet-header>…</bottom-sheet-header>   /* search field  */
  <bottom-sheet-content>…</bottom-sheet-content> /* results       */
</bottom-sheet>

// snap= sets the opening height; it reflects after that
Footer flex-shrink: 0

A floor that never travels.

Add <bottom-sheet-footer> and the sheet becomes a three-part column. Header and footer are fixed — both are flex-shrink: 0 — and only the content between them flexes and scrolls. Scroll the items below and the checkout bar stays exactly where your thumb expects it.

The footer also takes over the safe area. Without one, the dialog pads itself by env(safe-area-inset-bottom); the moment a footer appears, that padding moves into the footer instead, so its background runs all the way to the bottom edge of the screen rather than stopping short of the home indicator. Tune the inset with --bs-footer-padding — the safe area is added below whatever you set.

The footer is a drag surface too, so the sheet is still dismissible from the one part of it that's always within reach. 

<bottom-sheet>
  <bottom-sheet-header>…</bottom-sheet-header>   /* fixed  · drag surface */
  <bottom-sheet-content>…</bottom-sheet-content> /* flex: 1 · scrolls     */
  <bottom-sheet-footer>
    <button>Checkout</button>
  </bottom-sheet-footer>  /* fixed · owns the safe area */
</bottom-sheet>

/* bottom-sheet.css */
bottom-sheet-footer {
  padding: var(--bs-footer-padding, var(--bs-content-padding));
  padding-bottom: calc(var(--bs-footer-padding, var(--bs-content-padding)) + env(safe-area-inset-bottom, 0px));
}
Inset detached · all corners

Lift it off the edges.

Add the inset attribute and the sheet stops being welded to the bottom of the screen: all four corners take --bs-panel-border-radius, and --bs-panel-inset-x and --bs-panel-inset-bottom open a gap on three sides. It's pure CSS — :has(bottom-sheet[inset]) does the whole thing and no JavaScript runs.

The off-screen position has to be corrected too. The hidden state translates the sheet down by 100%, which is only the panel's own height — the moment there's a gap beneath it, that leaves the sheet peeking above the bottom edge by exactly the inset. The inset rules add the gap and the safe area back into that translation.

The footer needs a second correction. Normally it absorbs env(safe-area-inset-bottom) so its background runs under the home indicator, but a floating sheet's bottom margin already clears that — left alone you'd get the gap twice. 

<bottom-sheet inset>…</bottom-sheet>

dialog-panel:has(bottom-sheet[inset]) > dialog {
  left:  var(--bs-panel-inset-x);
  right: var(--bs-panel-inset-x);
  width: auto;
  border-radius: var(--bs-panel-border-radius);
  margin-bottom: calc(var(--bs-panel-inset-bottom) + env(safe-area-inset-bottom, 0px));
}

/* or it peeks by exactly the inset when hidden */
transform: translate3d(0, calc(100% + var(--bs-panel-inset-bottom) + env(safe-area-inset-bottom, 0px)), 0);
Combined inset + snap-points

Floating, and still snapping.

The two features touch the same element from opposite directions — one rewrites the dialog's off-screen transform, the other drives its height every frame of a drag. This is the combination most likely to break, so it gets its own sheet.

One honest quirk: with a bottom gap, height: 70dvh puts the top edge at 100 − 70 − inset from the bottom of the screen, so a floating sheet at a given snap sits slightly higher than an edge-anchored one at the same snap. Height is height — the snap describes the sheet, not the gap under it. 

<bottom-sheet inset snap-points="35,65,88">…</bottom-sheet>
Limit max-display-width 768

Above a certain width, it declines.

A sheet anchored to the bottom edge stops making sense on a wide screen. Set max-display-width="768" and the component enforces the boundary from both sides: show() returns early above the limit, and a throttled resize listener closes an already-open sheet the moment the viewport crosses it.

Narrow this window under 768px and open it, then widen the window and watch it leave.

Measuring the viewport… 
<bottom-sheet max-display-width="768">…</bottom-sheet>

// or from script — Infinity removes the limit
sheet.maxDisplayWidth = 768;
sheet.maxDisplayWidth = Infinity;
Theme --bs-*

Every hook, on one sheet.

The reference table further down lists the custom properties; this one lets you turn them. Nothing here is a component API — the controls write plain style.setProperty calls onto the <dialog-panel>, and inheritance carries them to the dialog, the handle, the padding, and the backdrop.

That's worth knowing on its own: because every hook is an inherited custom property, you can theme one sheet without touching any of the others, and without a single selector of your own. Set the dials first — an open modal makes everything behind it inert, so these controls are unreachable while the sheet is up. 

// what every control on this page actually does
panel.style.setProperty('--bs-panel-border-radius', '25px');

/* or, far more likely, in your own stylesheet */
#my-panel {
  --bs-panel-background: #171012;
  --bs-handle-color: #9a6a5a;
}
Lifecycle 4 events

Every open and close leaves a trace.

Events come from the parent <dialog-panel>, bubble, and are composed, so one listener on the panel — or on document — sees the whole cycle. beforeShow and beforeHide are cancelable; call preventDefault() in either to hold the sheet where it is.

Each event carries detail.state, which is also mirrored on the panel as a state attribute and is what drives the CSS animation: hidden → showing → shown → hiding. Open the sheet and close it to watch the sequence fill in. 

No events yet.
const panel = document.querySelector('#sheet-panel');

for (const name of ['beforeShow', 'shown', 'beforeHide', 'hidden']) {
  panel.addEventListener(name, (event) => {
    console.log(name, event.detail.state);
  });
}

// cancelable — this sheet refuses to open
panel.addEventListener('beforeShow', (event) => event.preventDefault());

Accessibility

Modal semantics, focus trapping, focus return, Escape handling, and body scroll lock are delegated to the native <dialog> via showModal(), driven by the parent panel — the sheet adds no ARIA of its own. Give the dialog an accessible name with aria-labelledby or aria-label, label icon-only close buttons, and keep a visible close control in the header for anyone who can't perform the gesture. Any element with data-action-hide-dialog closes the sheet.

Browser support

Modern browsers with custom elements, native <dialog>, Pointer Events, and :has(): Chrome 105+, Edge 105+, Safari 15.4+, Firefox 121+. Pointer Events mean mouse, pen, and touch all take the same path, so every gesture on this page works with a mouse.
